Abstract

HeatGuard is a working prototype of the heatwave early-warning use case. It uses real India Meteorological Department (IMD) gridded daily maximum-temperature data for 2014–2024, forecasts the maximum temperature for each of the next 7 days for ten Indian cities with machine-learning models, and converts every forecast day into a heatwave alert using IMD's published criteria. On the unseen year 2024 the forecast error grows from 0.883 °C (day 1) to 1.542 °C (day 7), lower than both baselines at every horizon. Next-day alerts detect 90% of actual heatwave city-days; alerts for days 5–7 are marked low-confidence because validation showed limited skill. The system is split into a FastAPI backend and an nginx-served web frontend, both published on Docker Hub (Experiment 2) and deployed on Kubernetes with scaling, self-healing, rollback and measured rolling updates (Experiment 3). The backend was right-sized from 2 vCPU / 2 GB to 1.25 vCPU / 192m with an estimated -42.7% change in hourly cost (Experiment 7), and three instance sizes were compared under the same workload against a target fixed in advance (Experiment 8). All results come from real runs; costs are estimates.

1. Problem statement, objectives and scope

Problem. Heatwaves in India are increasing in frequency, intensity and duration and affect public health, agriculture and economic activity. Severity varies by region, so timely, region-specific warnings are needed (use-case document KJS-CES-01, §6).

Objectives.

  1. Build an input → processing → output prototype on real IMD meteorological data (use case §11, steps 1–2).
  2. Develop AI models for region-wise maximum-temperature forecasting up to 7 days ahead and evaluate them against baselines (§8, objective 2).
  3. Classify heatwave severity per day, produce advisories and visualise them on a decision-support dashboard (§8, objective 4; §11, steps 7–9).
  4. Package, publish, deploy, measure and cost-optimise the service using Experiments 2, 3, 7 and 8.

2. Dataset

  • Source: IMD Pune, "High resolution 1°×1° daily gridded maximum temperature" binary data, imdpune.gov.in/cmpg/Griddata/Max_1_Bin.html (Srivastava, Rajeevan and Kshirsagar, 2009), the repository named in the use-case document (§11, step 1).
  • Format: one .GRD file per year, float32, 31 × 31 grid (7.5–37.5 °N, 67.5–97.5 °E), 99.9 = missing. File sizes were checked (1,403,060 bytes for 365-day years, 1,406,904 bytes for leap years).
  • Acquisition: scripts/download_imd.sh. The IMD server is slow and dropped connections (2017 needed three attempts), so the script retries and accepts only full-size files.
  • Pre-processing: scripts/prepare_data.py extracts the grid cell nearest to each of ten cities (Delhi, Jaipur, Lucknow, Patna, Ahmedabad, Nagpur, Kolkata, Bhubaneswar, Hyderabad, Chennai): 40,180 daily rows. Grid orientation was verified (sea cells missing, Ladakh cold, Delhi ≈ 17 °C in January and ≈ 40 °C in May).
  • Split (time-ordered by the forecast target day): train 2014–2022, validation 2023, test 2024. Day-1 samples: train 32800, validation 3650, test 3660.
  • No synthetic data is used. The data is non-personal meteorological data.

3. System architecture and tools

3.1 Why an early-warning service needs these cloud capabilities

A heatwave warning is most valuable exactly when demand peaks: during a hot spell many people open the dashboard at once, and the service cannot be down while it is being updated. Packaging the backend and frontend as separate images (Exp 2) means each can be rebuilt, versioned and moved to any machine unchanged. Running them on Kubernetes (Exp 3) adds replicas, health probes and self-healing, so a crashed pod does not take the warning offline, and rolling updates let a retrained model be released without an outage. Because such a service runs all year but is busy only in summer, paying for idle capacity is the main waste; Exp 7 measures how much of the allocated capacity is really used, and Exp 8 picks the cheapest size that still meets a stated response-time and throughput target.

4. AI component

The AI part is kept separate from the cloud part so each can be explained on its own.

4.1 Machine-learning forecaster (7 days ahead)

Method: direct multi-horizon forecasting. Seven separate models are trained; model h predicts the maximum temperature on day t + h from the 7 days up to day t. Features (app/features.py, shared by training and serving): the last 7 daily Tmax values, their mean, the target day's season (sine/cosine of day-of-year) and climatological normal (from 2014–2022 only), and the cell's latitude and longitude. Two model families (ridge regression, gradient boosting) were compared with two baselines: persistence (same as today) and climatology (the normal for that date). The family with the lowest mean validation error (ridge_regression, 1.516 °C) was deployed; 2024 was used only once, for the final numbers below.

4.2 Rule-based severity classifier (not ML)

app/severity.py applies the IMD heatwave definitions: a heatwave is considered only if Tmax ≥ 40 °C (plains) or ≥ 37 °C (coastal). Departure from normal 4.5–6.4 °C → Heatwave, > 6.4 °C → Severe heatwave; for plains, Tmax ≥ 45 °C → Heatwave and ≥ 47 °C → Severe. Coastal stations (Kolkata, Chennai) have only a Heatwave category.

4.3 Alert margin and confidence per forecast day

Regression pulls extreme values towards the mean, so a raw forecast rarely crosses the IMD thresholds (day 1 without a margin: recall 29%). Because a missed heatwave is costlier than a false alarm, each day's alert is issued on an upper-bound forecast (forecast + margin). The margin for each day was chosen on the 2023 validation year by F2 score (recall weighted over precision). Where the best validation F2 was below 0.3, that day's alerts are labelled low-confidence in the API and the dashboard. Validation contains only 14 heatwave city-days, so these choices are uncertain.

5. Application: backend and frontend

Backend (app/main.py, image ayushiranjan27/heatguard:2.0): a stateless FastAPI service. Endpoints: /health, /cities, /observed (IMD history with normals and the actual next 7 days), /outlook (7-day forecast for all 10 cities), /model-info (per-horizon metrics) and POST /predict (7-day forecast from 7 values). Input validation returns 404/422 with clear messages; interactive API docs are at /docs. Frontend (frontend/, image ayushiranjan27/heatguard-web:2.1): a static web app served by unprivileged nginx, which also reverse-proxies /api/ to the backend (and the backend's interactive docs at /api/docs), so the browser talks to one address and the backend can stay internal. It has two pages with one visual identity (a printed "heat bulletin": paper and ink for the interface, heat colours only for data, bundled fonts so nothing depends on the internet):

  • Landing page (/): an animated introduction whose figures all come from the live API: a hero card with the highest-risk city for 27 May 2024, a "heat stripes" band of every 2024 IMD daily maximum for Delhi, count-up key figures read from /model-info, a scroll-revealed explanation of the pipeline, a pulsing India map of the 10-city outlook, a per-day accuracy chart, and the four cloud experiments with their measured results. Animations respect the operating system's reduced-motion setting.
  • Dashboard (/dashboard): the 7-day heat bulletin for any city and date in 2014–2024: headline alert and advice, KPI row, a seven-day forecast table (forecast ± typical error, alert, alert basis, departure, the actual IMD value, confidence), a 30-day trend chart with uncertainty band, an India map and ranking, a what-if form, and the reliability panel.

The map uses bundled Natural Earth boundaries (India point-of-view edition), so it works without an internet map service. Version 2.0 of the frontend (a single dark dashboard) is kept in the archive; 2.1 changed only the frontend, so the backend and all measurements are unchanged.

Experiment 3: Application Deployment using Kubernetes

Aim (manual): deploy an application using Kubernetes, use kubectl commands and expose an app (preferably the image created in the Docker experiment). Use-case connection: both HeatGuard images from Docker Hub run as replicated, self-healing Deployments, as an early-warning service must stay available, including while it is updated.

Procedure. The manual used the Killercoda playground; this project used kind (Kubernetes-in-Docker), a real Kubernetes cluster running locally, so every step could be scripted (experiments/exp3_kubernetes.sh) and logged. The backend is a ClusterIP Service (internal only); the frontend is a NodePort Service on 30080 and finds the backend by its Kubernetes DNS name. Both Deployments use maxSurge: 1, maxUnavailable: 0 and a 5-second preStop delay. The backend's CPU/memory limits are read from the Experiment 7 right-sizing decision.

k8s/api.yaml
# Experiment 3: HeatGuard backend API (7-day forecast). Image from Docker Hub (Experiment 2).
# Internal only: ClusterIP service, reached by the frontend through its /api/ proxy.
# Resource limits = right-sized values measured in Experiment 7.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: heatguard-api
  labels: {app: heatguard-api, tier: backend}
spec:
  replicas: 2
  selector:
    matchLabels: {app: heatguard-api}
  strategy:
    type: RollingUpdate
    rollingUpdate: {maxSurge: 1, maxUnavailable: 0}   # never drop below the desired replica count
  template:
    metadata:
      labels: {app: heatguard-api, tier: backend}
    spec:
      terminationGracePeriodSeconds: 20
      containers:
        - name: api
          image: docker.io/DOCKERHUB_USER/heatguard:2.0
          imagePullPolicy: Always
          ports:
            - containerPort: 8000
          resources:
            requests: {cpu: 250m, memory: 128Mi}
            limits: {cpu: API_CPU_LIMIT, memory: API_MEM_LIMIT}
          readinessProbe:
            httpGet: {path: /health, port: 8000}
            initialDelaySeconds: 3
            periodSeconds: 5
          livenessProbe:
            httpGet: {path: /health, port: 8000}
            initialDelaySeconds: 10
            periodSeconds: 10
          lifecycle:
            preStop:
              exec: {command: ["sleep", "5"]}   # let the Service remove this pod before it stops

kind: Service

  name: heatguard-api

Experiment 7: Cloud Cost Optimization through Resource Right-Sizing

Aim (manual): analyse CPU and memory utilisation of an over-provisioned workload, apply right-sizing and measure cost and efficiency improvements without performance degradation. Use-case connection: the workload is the HeatGuard v2 backend itself, answering 7-day forecast requests built from real 2024 IMD data.

Procedure. (1) Run ayushiranjan27/heatguard:2.0 with 2 vCPU / 2 GB (docker run --cpus 2 --memory 2g). (2) Send the fixed workload: 15,000 POST /predict requests, 20 concurrent clients, 100 warm-up requests, fixed seed (loadtest/loadtest.py), while sampling docker stats about once per second. (3) Repeat 3 times. (4) Right-size with the manual's rule, "slightly above peak with a safety buffer" (experiments/rightsize.py): CPU = peak × 1.25 rounded up to 0.25 vCPU; memory = peak × 1.5 rounded up to 64 MiB. (5) Re-run the same workload 3 times with the new limits. (6) Estimate cost.

Right-sizing decision: observed peak 0.868 cores and 118.2 MiB → 1.25 vCPU / 192m. These values are used as the backend limits in Kubernetes (Exp 3).

Given the -42.7% estimated cost change, this trade-off is acceptable for this service.

Experiment 8: FinOps Principles and Instance-Type Comparison

Aim (manual): compare different instance (resource) configurations for the same workload and identify the most cost-efficient option without performance degradation. Use-case connection: chooses the cheapest size on which the heatwave API still meets its service target.

Procedure (manual algorithm steps 1–10). Workload identical to Experiment 7. Candidates: three AWS Fargate-valid sizes, emulated with Docker limits. The performance target was written down before running (experiments/exp8_configs.json), using the rule: At most 25% lower throughput and at most 50% higher p95 latency than the over-provisioned reference (2 vCPU / 2 GB: ~417 req/s, p95 ~162 ms), no errors, no OOM kill. This gives throughput ≥ 300 req/s, p95 latency ≤ 250 ms, zero errors and no OOM kill. Each configuration ran 3 times.

9. Limitations, data privacy and improvements

  • Spatial resolution: 1° grid cells (~100 km) are averages, not station readings.
  • Forecast inputs: temperature history and season only (no humidity, wind or numerical weather model); skill at days 5–7 is close to climatology.
  • Alerts: per cell per day; IMD declares heatwaves when criteria hold at ≥ 2 stations of a sub-division for 2 consecutive days. Normals come from 2014–2022, not 30-year station normals. Margins were tuned on a validation year with only 14 heatwave city-days; precision is low at longer horizons.
  • Historical replay: the dashboard forecasts from any date in 2014–2024 using IMD archives; it is not connected to a live data feed.
  • Experiments 7 and 8: instance sizes were emulated with Docker limits on one laptop; the single Python load generator limits throughput; costs are estimates.
  • Experiment 3: single-node local cluster, not a cloud VM.
  • Data privacy: only public, non-personal weather data; no user data stored; both containers run as non-root users; the backend is not exposed outside the cluster; no credentials in the repository.
  • Improvements: humidity/heat-index inputs and IMD forecast products; consecutive-day rule; calibrated uncertainty (quantile regression); scheduled data refresh; LLM multilingual advisories with human review (use case §13); Horizontal Pod Autoscaler; repeat Experiments 7–8 on real cloud instances.

10. Version history

v1.0/1.1: single FastAPI container with a built-in dashboard and a next-day forecast; v1.1 corrected the coastal heatwave rule. v2.0: 7-day forecast, separate backend and frontend images, two-tier Kubernetes deployment with zero-downtime settings. Frontend 2.1 (current): new landing page and redesigned dashboard; frontend-only change, released with a measured rolling update. Backend stays 2.0. All v1 experiment logs and measurements are kept unchanged in experiments/results/archive_v1/; every v2 experiment was re-run with the same scripts.

11. Conclusion

HeatGuard turns real IMD observations into 7-day maximum-temperature forecasts and IMD-style heatwave alerts, with each day's reliability measured and shown to the user. The same two images were containerised and published (Exp 2), operated on Kubernetes with scaling, recovery and rolling updates (Exp 3), right-sized from measured usage (Exp 7) and sized against an explicit service target (Exp 8). Each experiment acts on the same artifacts, so together they form one pipeline from data and model to a cost-aware, resilient deployment.
