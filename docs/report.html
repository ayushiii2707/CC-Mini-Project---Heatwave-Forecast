Abstract

HeatGuard is a working prototype of the heatwave early-warning use case. It reads real India Meteorological Department (IMD) gridded daily maximum-temperature data for 2014–2024, forecasts the next day's maximum temperature for ten Indian cities with a machine-learning model, and converts the forecast into a heatwave alert using IMD's published criteria. On the unseen year 2024 the deployed ridge-regression model has a mean absolute error of 0.883 °C (persistence baseline 0.94 °C), and the alert logic detects 89.6% of the 48 actual heatwave city-days with a precision of 56.6%. The service is containerised and published on Docker Hub (Experiment 2), deployed on a Kubernetes cluster with scaling, self-healing, rollback and a rolling update (Experiment 3), right-sized from 2 vCPU / 2 GB to 0.75 vCPU / 192m with an estimated -65.2% change in hourly cost (Experiment 7), and compared across three instance sizes under the same workload to find the cheapest size meeting a pre-defined performance target (Experiment 8). All results in this report come from real runs; costs are estimates.

1. Problem statement, objectives and scope

Problem. Heatwaves in India are increasing in frequency, intensity and duration and affect public health, agriculture and economic activity. Severity varies by region, so timely, region-specific warnings are needed (Use-case document KJS-CES-01, §6).

Objectives.

  1. Build an input → processing → output prototype on real IMD meteorological data (use case §11, steps 1–2).
  2. Develop an AI model for region-wise maximum-temperature forecasting and evaluate it against a baseline (§8, objective 2).
  3. Classify heatwave severity and produce an advisory (§8, objective 4; §11, steps 8–9).
  4. Package, publish, deploy, measure and cost-optimise the service using Experiments 2, 3, 7 and 8.

2. Dataset

  • Source: IMD Pune, "High resolution 1°×1° daily gridded maximum temperature" binary data, imdpune.gov.in/cmpg/Griddata/Max_1_Bin.html (Srivastava, Rajeevan and Kshirsagar, 2009). This is the repository named in the use-case document (§11, step 1).
  • Format: one .GRD file per year, float32, 31 × 31 grid (7.5–37.5 °N, 67.5–97.5 °E), 99.9 = missing. File sizes were checked: 1,403,060 bytes for 365-day years and 1,406,904 bytes for leap years.
  • Acquisition: scripts/download_imd.sh. The IMD server is slow and dropped connections (2017 needed three attempts), so the script retries and accepts only full-size files.
  • Pre-processing: scripts/prepare_data.py parses the grid, extracts the cell nearest to each of ten cities (Delhi, Jaipur, Lucknow, Patna, Ahmedabad, Nagpur, Kolkata, Bhubaneswar, Hyderabad, Chennai) and writes 40,180 daily rows. Grid orientation was verified (sea cells missing, Ladakh cold, Delhi ≈ 17 °C in January and ≈ 40 °C in May).
  • Split (time-ordered): train 2014–2022 (32800 samples), validation 2023 (3650), test 2024 (3660).
  • No synthetic data is used. The data is non-personal meteorological data, so no personal-data privacy issues arise.

4. AI component

The AI part is kept separate from the cloud part so each can be explained on its own.

4.1 Machine-learning forecaster (next-day maximum temperature)

Input features (app/features.py, shared by training and serving): the last 7 daily Tmax values, their mean, day-of-year as sine/cosine, the climatological normal for the target day (from 2014–2022 only, to avoid leakage), and the cell's latitude and longitude. Target: Tmax on the next day. Three approaches were compared; the model with the lowest validation error was deployed and the test year was used only once for final reporting.

ModelValidation MAE 2023 (°C)Test MAE 2024 (°C)Test RMSE 2024 (°C)
persistence_baseline0.9240.941.303
ridge_regression (deployed)0.8880.8831.225
gradient_boosting0.8950.9021.248

Test MAE by city (°C): Ahmedabad 0.724, Bhubaneswar 0.869, Chennai 0.74, Delhi 1.057, Hyderabad 0.818, Jaipur 0.913, Kolkata 0.88, Lucknow 0.989, Nagpur 0.825, Patna 1.015.

Interpretation: the ML model is about 6% more accurate than the persistence baseline. Day-to-day temperature is strongly persistent, so the gain is modest but consistent; the simpler linear model generalised slightly better than gradient boosting.

4.2 Rule-based severity classifier (not ML)

app/severity.py applies the IMD heatwave definitions (IMD, Heat wave definitions): a heatwave is considered only if Tmax ≥ 40 °C (plains) or ≥ 37 °C (coastal). Departure from normal 4.5–6.4 °C → Heatwave, > 6.4 °C → Severe heatwave; for plains, Tmax ≥ 45 °C → Heatwave and ≥ 47 °C → Severe. Coastal stations have only a Heatwave category. Kolkata and Chennai are treated as coastal.

4.3 Alert margin (finding and fix)

Evaluated directly on the forecast, alerts detected only 29.2% of real heatwave days: regression pulls extreme values towards the mean, so the forecast rarely crossed the IMD thresholds. Because a missed heatwave is costlier than a false alarm, alerts are issued on an upper-bound forecast (forecast + margin). The margin was chosen on the 2023 validation year by F2 score (which weights recall above precision): margin 1.25 °C. The 2023 year contains only 14 heatwave city-days, so this choice is uncertain.

Alert method (test 2024, 48 actual heatwave city-days)RecallPrecisionF2
ML forecast + 1.25 °C margin (deployed)0.8960.5660.802

Confusion matrix of the deployed alert on 2024 (rows = actual, columns = predicted; Normal / Heatwave / Severe): [3579, 33, 0], [5, 37, 2], [0, 3, 1]. The system detects most heatwave days but about 4 in 10 alerts are false alarms.

Experiment 3: Application Deployment using Kubernetes

Aim (manual): deploy an application using Kubernetes, use kubectl commands and expose an app (preferably the image created in the Docker experiment). Use-case connection: the HeatGuard image from Docker Hub is deployed as a replicated, self-healing service, as an early-warning service must stay available. Resource limits come from Experiment 7.

Procedure. The manual used the Killercoda playground; this project used kind (Kubernetes-in-Docker), a real Kubernetes cluster running locally on Docker Desktop, so the full sequence could be scripted (experiments/exp3_kubernetes.sh) and logged. Steps: create cluster → apply Deployment (2 replicas) and NodePort Service → access through the Service → scale to 3 → delete a pod → set a non-existent image tag → roll back → rolling update to 1.1.

k8s/deployment.yaml
# Experiment 3: HeatGuard Deployment. Image is pulled from Docker Hub (Experiment 2).
# CPU/memory limits are the right-sized values measured in Experiment 7.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: heatguard
  labels: {app: heatguard}
spec:
  replicas: 2
  selector:
    matchLabels: {app: heatguard}
  template:
    metadata:
      labels: {app: heatguard}
    spec:
      containers:
        - name: heatguard
          image: docker.io/DOCKERHUB_USER/heatguard:1.1
          imagePullPolicy: Always
          ports:
            - containerPort: 8000
          resources:
            requests: {cpu: 250m, memory: 128Mi}
            limits: {cpu: 750m, memory: 192Mi}
          readinessProbe:
            httpGet: {path: /health, port: 8000}
            initialDelaySeconds: 3
            periodSeconds: 5
          livenessProbe:
            httpGet: {path: /health, port: 8000}
            initialDelaySeconds: 10
            periodSeconds: 10

Experiment 7: Cloud Cost Optimization through Resource Right-Sizing

Aim (manual): analyse CPU and memory utilisation of an over-provisioned workload, apply right-sizing and measure cost and efficiency improvements without performance degradation. Use-case connection: the workload is the HeatGuard forecast API itself, loaded with forecast requests built from real 2024 IMD data.

Procedure. (1) Run the heatguard image with 2 vCPU / 2 GB (docker run --cpus 2 --memory 2g). (2) Send the fixed workload: 15,000 POST /predict requests, 20 concurrent clients, 100 warm-up requests, fixed random seed (loadtest/loadtest.py), while sampling docker stats about once per second. (3) Repeat 3 times. (4) Right-size with the manual's rule, "slightly above peak with a safety buffer" (experiments/rightsize.py): CPU = peak × 1.25 rounded up to 0.25 vCPU; memory = peak × 1.5 rounded up to 64 MiB. (5) Re-run the same workload 3 times with the new limits. (6) Estimate cost.

Right-sizing decision (from rightsizing_decision.json): observed peak 0.566 cores and 105.5 MiB → 0.75 vCPU / 192m.

8. Limitations, data privacy and improvements

  • Spatial resolution: 1° grid cells (~100 km) are averages, not station readings; city values are approximations.
  • Forecast horizon: one day ahead only; uses only past temperature (no humidity, wind or numerical weather model input).
  • Heatwave rules: applied per cell per day; IMD declares heatwaves when criteria hold at ≥ 2 stations of a sub-division for 2 consecutive days. Normals come from 2014–2022 rather than IMD's 30-year station normals.
  • Alert margin: tuned on a validation year with only 14 heatwave city-days; precision is 0.57 (many false alarms).
  • Experiments 7 and 8: instance sizes were emulated with Docker limits on one laptop, not cloud VMs; the single Python load generator limited throughput to ~600 req/s; costs are estimates from public prices.
  • Experiment 3: single-node local cluster; one failed health check during the rolling update.
  • Data privacy: only public, non-personal meteorological data is processed; no user data is stored; the container runs as a non-root user; Docker Hub credentials were kept out of the code and repository (.env.example holds only the username variable).
  • Improvements: add humidity/heat-index and IMD forecast inputs; multi-day forecasts; consecutive-day rule; quantile regression for calibrated uncertainty; LLM-generated multilingual advisories with human review (use case §13); Horizontal Pod Autoscaler and preStop hooks; repeat Experiments 7–8 on real cloud instances.

9. Conclusion

A working heatwave early-warning prototype was built on real IMD data. Its ML forecaster beats a persistence baseline, and the validated alert margin raises heatwave detection on the unseen 2024 year from 29% to 90%. The same service was containerised and published (Exp 2), deployed and operated on Kubernetes (Exp 3), right-sized for an estimated 65% cost reduction (Exp 7), and compared across instance sizes to choose the cheapest one meeting a stated target (Exp 8). Each experiment acts on the same artifact, so together they form one pipeline from model to cost-optimised deployment.
