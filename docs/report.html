2. Abstract

HeatGuard is a working prototype of the heatwave early-warning use case. It uses real India Meteorological Department (IMD) gridded daily maximum-temperature data for 2014–2024, forecasts the maximum temperature for each of the next 7 days for ten Indian cities with machine-learning models, and converts every forecast day into a heatwave alert using IMD's published criteria. On the unseen year 2024 the forecast error grows from 0.883 °C (day 1) to 1.542 °C (day 7), lower than both baselines at every horizon; next-day alerts detect 90% of actual heatwave city-days, and alerts for days 5–7 are labelled low-confidence. The system is a FastAPI backend and an nginx-served frontend (animated landing page and dashboard). Experiment 2 packages both as Docker images and publishes them on Docker Hub; Experiment 3 runs them on Kubernetes with scaling, self-healing, rollback and zero-downtime rolling updates; Experiment 7 right-sizes the backend from measured usage (estimated hourly cost -42.7%); Experiment 8 compares three instance sizes under the same workload against a target fixed in advance. All results come from real runs on the student's machine; costs are estimates.

3. Problem statement, objectives and scope

Problem. Heatwaves in India are increasing in frequency, intensity and duration and affect public health, agriculture and economic activity. Severity varies by region, so timely, region-specific warnings are needed (use-case document KJS-CES-01, §6).

  3. Classify heatwave severity per day, produce advisories and visualise them on a decision-support dashboard (§8, objective 4; §11, steps 7–9).

4. Dataset

  • Source: IMD Pune, "High resolution 1°×1° daily gridded maximum temperature", imdpune.gov.in/cmpg/Griddata/Max_1_Bin.html (Srivastava, Rajeevan and Kshirsagar, 2009), the repository named in the use-case document (§11, step 1).
  • Format: one .GRD file per year, float32, 31 × 31 grid (7.5–37.5 °N, 67.5–97.5 °E), 99.9 = missing; file sizes checked (1,403,060 bytes for 365-day years, 1,406,904 for leap years).
  • Acquisition: scripts/download_imd.sh; the IMD server is slow and dropped connections (2017 needed three attempts), so the script retries and accepts only full-size files.
  • Pre-processing: scripts/prepare_data.py extracts the grid cell of each of ten cities (Delhi, Jaipur, Lucknow, Patna, Ahmedabad, Nagpur, Kolkata, Bhubaneswar, Hyderabad, Chennai): 40,180 daily rows; grid orientation verified (sea cells missing, Ladakh cold, Delhi ≈ 17 °C in January and ≈ 40 °C in May).
  • Split (by forecast target day): train 2014–2022, validation 2023, test 2024 (day-1 samples 32800 / 3650 / 3660).
  • No synthetic data is used; the data is non-personal meteorological data.

5. System architecture and tools

5.1 Why an early-warning service needs these cloud capabilities

A heatwave warning is most valuable exactly when demand peaks: during a hot spell many people open the dashboard at once, and the service cannot be down while it is being updated. Packaging the backend and frontend as separate images (Exp 2) means each can be rebuilt, versioned and moved to any machine unchanged. Running them on Kubernetes (Exp 3) adds replicas, health probes and self-healing, so a crashed pod does not take the warning offline, and rolling updates let a retrained model or a new interface be released without an outage. Because such a service runs all year but is busy mainly in summer, paying for idle capacity is the main waste; Exp 7 measures how much of the allocated capacity is really used, and Exp 8 picks the cheapest size that still meets a stated response-time and throughput target.

6.1 How the heatwave use case motivates each experiment

Exp 2A warning system must be deployable anywhere, identically. A district control room, a university server or a cloud VM must run exactly the forecasting service that was validated. Docker images freeze the code, the 7 trained models and the IMD data together; Docker Hub lets anyone pull them for Intel or Apple machines.
Exp 3Warnings must stay online during the heat peak and during updates. Kubernetes keeps several copies of each service, replaces failed ones, scales the public frontend when many people check the forecast, and rolls out a retrained model or a new interface without dropping requests (measured).
Exp 7The service runs all year but is busy mainly in summer. Reserving large machines "to be safe" wastes money for most of the year. Measuring the backend under a realistic forecast load shows how much CPU and memory it actually needs, and those limits are applied in Kubernetes.
Exp 8Public money should buy the cheapest service that still meets its promise. A target is stated first (how many forecasts per second, how fast), then instance sizes are compared on cost per million forecasts, so the choice is based on value rather than on the lowest price.

7. AI component

The AI part is kept separate from the cloud part so each can be explained on its own.

7.1 Machine-learning forecaster (7 days ahead)

Direct multi-horizon forecasting: seven separate models; model h predicts the maximum temperature on day t + h from the 7 days up to day t. Features (app/features.py, shared by training and serving): the last 7 daily Tmax values, their mean, the target day's season (sine/cosine of day-of-year) and climatological normal (from 2014–2022 only), and the cell's latitude and longitude. Two model families (ridge regression, gradient boosting) were compared with two baselines, persistence (same as today) and climatology (the normal for that date). The family with the lowest mean validation error (ridge_regression, 1.516 °C) was deployed; 2024 was used only once, for the numbers below.

7.2 Rule-based severity classifier (not ML)

app/severity.py applies the IMD heatwave definitions: a heatwave is considered only if Tmax ≥ 40 °C (plains) or ≥ 37 °C (coastal). Departure from normal 4.5–6.4 °C → Heatwave, > 6.4 °C → Severe heatwave; for plains, Tmax ≥ 45 °C → Heatwave and ≥ 47 °C → Severe. Coastal stations (Kolkata, Chennai) have only a Heatwave category.

7.3 Alert margin and confidence per forecast day

Regression pulls extreme values towards the mean, so a raw forecast rarely crosses the IMD thresholds (day 1 without a margin: recall 29%). Because a missed heatwave is costlier than a false alarm, each day's alert uses an upper-bound forecast (forecast + margin); the margin for each day was chosen on 2023 by F2 score. Where the best validation F2 was below 0.3, that day's alerts are labelled low-confidence. Validation contains only 14 heatwave city-days, so these choices are uncertain.

8. Application: landing page, dashboard and API

Backend (app/main.py, image ayushiranjan27/heatguard:2.0): a stateless FastAPI service with /health, /cities, /observed (IMD history with normals and the actual next 7 days), /outlook (all 10 cities), /model-info (per-horizon metrics) and POST /predict (7-day forecast). Invalid input returns 404/422 with clear messages; interactive docs at /docs.

Frontend (frontend/, image ayushiranjan27/heatguard-web:2.1): unprivileged nginx serving two pages and reverse-proxying /api/ (and the API docs at /api/docs) to the backend, so the browser talks to one address and the backend stays internal. One visual identity (a printed "heat bulletin": paper and ink for the interface, heat colours only for data; fonts and libraries bundled so nothing depends on the internet):

  • Landing page (/): animated introduction whose figures all come from the live API: the highest-risk city for 27 May 2024, a "heat stripes" band of every 2024 IMD daily maximum for Delhi, count-up key figures, the pipeline, a pulsing India map of the 10-city outlook, per-day accuracy and the four experiments. Animations respect the reduced-motion setting.
  • Dashboard (/dashboard): 7-day heat bulletin for any city and date in 2014–2024: headline alert and advice, KPIs, a seven-day forecast table with the actual IMD values, trend chart with uncertainty band, India map and ranking, what-if form, reliability panel.

9. Implementation of the four experiments

9.1 Experiment 2: Containerization, Docker and Docker Hub

Aim (manual). Install Docker, pull and run images from Docker Hub, modify containers to run an application, and push it to Docker Hub.

About the experiment. A Docker image is a read-only, layered template holding an application with all its dependencies; a container is a running instance of that image. A registry such as Docker Hub stores images so that any machine can pull and run exactly the same software.

Where Experiment 2 comes into play in HeatGuard

Experiment 2 is the packaging and publishing stage. The backend image bakes in the API code, the 7 trained models, their metrics and the IMD city series, so the forecast that was evaluated is the forecast that is served. The frontend image holds the landing page, dashboard and the nginx proxy. Docker Compose runs them together; Docker Hub distributes them. Every later experiment uses these exact images: Kubernetes pulls them (Exp 3) and the backend image is the workload measured in Exp 7 and Exp 8.

Files: Dockerfile, frontend/Dockerfile, frontend/nginx/default.conf.template, docker-compose.yml, .dockerignore, experiments/exp2_docker.sh, experiments/release_frontend.sh.

Procedure. (1) Docker Desktop installed; Docker Hub account ayushiranjan27 created and docker login done by the student. (2) Manual tasks: nginx pulled and run on port 8080, hello-world and Ubuntu run, Docker commands explored, nginx pushed as ayushiranjan27/nginx-exp2:1.0. (3) Dockerfiles and Compose file written. (4) Both images built, run together, tested through the frontend proxy including failure cases. (5) Both pushed for arm64 and amd64 with docker buildx. (6) Local images deleted, pulled back from Docker Hub and run. (7) The redesigned frontend was released as 2.1 the same way.

9.2 Experiment 3: Application Deployment using Kubernetes

Aim (manual). Deploy an application using Kubernetes; use kubectl commands; expose an application, preferably the image created in the Docker experiment.

About the experiment. Kubernetes manages containers declaratively: a Deployment states how many copies (pods) of an image should run, a ReplicaSet enforces that number, and a Service gives the pods a stable address and balances traffic between them. Probes, rolling updates and rollbacks let an application keep running while it fails, scales or changes.

Where Experiment 3 comes into play in HeatGuard

Experiment 3 is the operating stage. The two Docker Hub images from Experiment 2 run as two Deployments on a kind cluster. The backend is internal (ClusterIP) and is reached only through the frontend, which is the public entry point (NodePort 30080). The backend's CPU/memory limits are the values measured in Experiment 7. The experiment demonstrates exactly what a warning service needs: replicas, self-healing, scaling, safe rollback of a bad release and updates with zero dropped requests.

Files: k8s/kind-config.yaml, k8s/api.yaml, k8s/web.yaml, experiments/exp3_kubernetes.sh, experiments/release_frontend.sh. The manual used the Killercoda playground; this project used kind (Kubernetes-in-Docker), a real Kubernetes cluster running locally, so every step could be scripted and logged.

Configuration.

k8s/api.yaml
# Experiment 3: HeatGuard backend API (7-day forecast). Image from Docker Hub (Experiment 2).
# Internal only: ClusterIP service, reached by the frontend through its /api/ proxy.
# Resource limits = right-sized values measured in Experiment 7.
apiVersion: apps/v1
kind: Deployment
metadata:
  name: heatguard-api
  labels: {app: heatguard-api, tier: backend}
spec:
  replicas: 2
  selector:
    matchLabels: {app: heatguard-api}
  strategy:
    type: RollingUpdate
    rollingUpdate: {maxSurge: 1, maxUnavailable: 0}   # never drop below the desired replica count
  template:
    metadata:
      labels: {app: heatguard-api, tier: backend}
    spec:
      terminationGracePeriodSeconds: 20
      containers:
        - name: api
          image: docker.io/DOCKERHUB_USER/heatguard:2.0
          imagePullPolicy: Always
          ports:
            - containerPort: 8000
          resources:
            requests: {cpu: 250m, memory: 128Mi}
            limits: {cpu: API_CPU_LIMIT, memory: API_MEM_LIMIT}
          readinessProbe:
            httpGet: {path: /health, port: 8000}
            initialDelaySeconds: 3
            periodSeconds: 5
          livenessProbe:
            httpGet: {path: /health, port: 8000}
            initialDelaySeconds: 10
            periodSeconds: 10
          lifecycle:
            preStop:
              exec: {command: ["sleep", "5"]}   # let the Service remove this pod before it stops

kind: Service

9.3 Experiment 7: Cloud Cost Optimization through Resource Right-Sizing

Aim (manual). Analyse CPU and memory utilisation of an over-provisioned workload, apply right-sizing, and measure cost and efficiency improvements without performance degradation.

About the experiment. Over-provisioning means reserving more CPU and memory than a workload uses, which costs money and energy without benefit. Right-sizing measures real usage under a representative load and sets limits slightly above the observed peak, then checks that performance holds.

Where Experiment 7 comes into play in HeatGuard

Experiment 7 is the measurement stage. The workload is the HeatGuard backend image itself, answering 15,000 real 7-day forecast requests built from 2024 IMD data. The right-sized limits are not just reported: they are written into the backend Deployment in Experiment 3, and the same workload and cost model are reused in Experiment 8.

Files: loadtest/loadtest.py, experiments/run_config.py, experiments/rightsize.py, experiments/summarize.py, results in experiments/results/exp7/.

Procedure. (1) Run ayushiranjan27/heatguard:2.0 with 2 vCPU / 2 GB. (2) Send the fixed workload (15,000 POST /predict, 20 concurrent clients, 100 warm-up requests, fixed seed) while sampling docker stats about once per second; repeat 3 times. (3) Apply the manual's rule, "slightly above peak with a safety buffer": CPU = peak × 1.25 rounded up to 0.25 vCPU; memory = peak × 1.5 rounded up to 64 MiB. (4) Re-run the same workload 3 times with the new limits. (5) Estimate cost.

Right-sizing decision: observed peak 0.868 cores and 118.2 MiB → 1.25 vCPU / 192m.

9.4 Experiment 8: FinOps Principles and Instance-Type Comparison

Aim (manual). Compare different instance (resource) configurations for the same workload and identify the most cost-efficient option without performance degradation.

About the experiment. FinOps treats cloud spending as a shared engineering and finance decision whose goal is value per unit cost, not the lowest bill. Comparing instance sizes on the same workload, against a stated performance target, shows which size delivers the required service most cheaply.

Where Experiment 8 comes into play in HeatGuard

Experiment 8 is the sizing decision. It reuses the Experiment 7 image, workload and cost model, and asks: if HeatGuard must serve at least 300 forecasts per second with p95 latency under 250 ms, which instance size does that most cheaply? The answer informs how large each backend replica in the Kubernetes deployment should be.

Files: experiments/exp8_configs.json (target + sizes, written before running), experiments/run_config.py, experiments/summarize.py, results in experiments/results/exp8/.

Procedure (manual algorithm steps 1–10). Workload identical to Experiment 7. Candidates: three AWS Fargate-valid sizes emulated with Docker limits. Target rule: At most 25% lower throughput and at most 50% higher p95 latency than the over-provisioned reference (2 vCPU / 2 GB: ~417 req/s, p95 ~162 ms), no errors, no OOM kill. → throughput ≥ 300 req/s, p95 ≤ 250 ms, zero errors, no OOM kill. 12. Limitations, data privacy and improvements

  • Spatial resolution: 1° grid cells (~100 km) are averages, not station readings.
  • Forecast inputs: temperature history and season only; skill at days 5–7 is close to climatology.
  • Alerts: per cell per day; IMD declares heatwaves when criteria hold at ≥ 2 stations of a sub-division for 2 consecutive days. Normals come from 2014–2022. Margins were tuned on a validation year with only 14 heatwave city-days; precision is low at longer horizons.
  • Historical replay: the dashboard forecasts from any date in 2014–2024 using IMD archives; it is not connected to a live feed.
  • Experiments 7 and 8: instance sizes were emulated with Docker limits on one laptop; the single Python load generator limits throughput; costs are estimates.
  • Experiment 3: single-node local cluster rather than a cloud VM.
  • Data privacy: only public, non-personal weather data; no user data stored; both containers run as non-root users; the backend is not exposed outside the cluster; no credentials in the repository.
  • Improvements: humidity/heat-index inputs and IMD forecast products; consecutive-day rule; calibrated uncertainty; scheduled data refresh; LLM multilingual advisories with human review (use case §13); Horizontal Pod Autoscaler; repeat Experiments 7–8 on real cloud instances.

14. Conclusion

HeatGuard turns real IMD observations into 7-day maximum-temperature forecasts and IMD-style heatwave alerts, with each day's reliability measured and shown to the user. The same two images were containerised and published (Exp 2), operated on Kubernetes with scaling, recovery and zero-downtime updates (Exp 3), right-sized from measured usage with the limits fed back into the deployment (Exp 7), and sized against an explicit service target (Exp 8). Because each experiment acts on the same artifacts and hands its result to the next, together they form one pipeline from data and model to a cost-aware, resilient early-warning service.
